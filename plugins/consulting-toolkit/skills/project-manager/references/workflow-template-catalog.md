# workflow.html テンプレート（活動カタログ型）

月次継続型プロジェクトの初期化時、共通シェル [../assets/workflow-template.html](../assets/workflow-template.html) をプロジェクトルートに `workflow.html` としてコピーし、本ファイルの指定に従って節を埋める。

**作業状態の正本は `workflow.html` 一本**である。Markdown 版は作らない（本文一箇所ルール）。状態が変わったら HTML の該当節を Edit で直接書き換える。

## 適用条件

以下の特徴を持つプロジェクトに適用する。

- 期限・最終ゴールが固定されない月次継続の業務委託・顧問契約である
- 支援内容が「順序性のない活動の集合」であり、ステップの順次進行になじまない
- 定例MTG・月次レポート等の月次サイクルが存在する
- 新規施策・改善提案が随時発生する

明確な納期と最終成果物を持つ単発案件には適用しない（調査型または他類型を使う）。

## 節構成（共通シェルからの差分）

| 節 | 内容 | 活動カタログ型での扱い |
|----|------|--------------------|
| 1 | 基本情報・ファイル配置・連携リンク | ワークフロー類型に「活動カタログ型（カスタム）」、形態に「月次継続型の業務委託（期限・最終ゴールは固定されない）」、管理方針に「進捗ステップ型ではなく、活動カタログ＋履歴ログで管理する」と書く。完了条件・解散条件の行は削除する |
| 2 | 現在の状態 | **表版に差し替え、見出しを「進行中の活動」にする**。セッションをまたいで続く活動のみ載せる |
| 3 | 作業計画（WBS） | **「活動カタログ」に差し替える**（下記）。マイルストーン・ゲート・ガントは持たない（順序・進捗の概念がないため）。月次サイクルの期日管理が必要なら 3.1 に月次カレンダー表を置いてよい |
| 4 | 成果物リンク | 直近の成果物のみ載せる。過去分は第6.2節の履歴ログで追う |
| 5 | タスク（積み残し） | そのまま使う |
| 6 | 運用記録 | そのまま使う。活動の完了は第6.2節の履歴ログに1行追記して表す |

## 第2節: 進行中の活動

セッションをまたいで続く活動のみステータス付きで管理する。単発で完結する活動はここに載せず、履歴ログにのみ記録する。

```html
<table class="report-table">
  <thead>
    <tr><th>活動</th><th>ステータス</th><th>開始日</th><th>備考</th></tr>
  </thead>
  <tbody>
    <tr><td class="name">{{活動名}}</td><td>in_progress</td><td class="num">{{YYYY-MM-DD}}</td><td>{{次のアクション・待ち先}}</td></tr>
  </tbody>
</table>
```

## 第3節: 活動カタログ

支援内容を活動タイプ別に整理する。各活動は必要に応じて随時起動する（順序や進捗の概念は持たない）。カテゴリは支援内容に応じて必要な数だけ設ける。

```html
<h3 class="sub-head"><span class="num">3.1</span>A. 月次サイクル活動</h3>
<p>毎月の定例運用で発生する活動。</p>

<table class="report-table">
  <thead>
    <tr><th>活動</th><th>担当</th><th>連携スキル</th><th>成果物格納先</th></tr>
  </thead>
  <tbody>
    <tr><td class="name">月次定例MTG準備（アジェンダ・資料作成）</td><td>AI</td><td>—</td><td><code class="mono">Meeting/YYYY-MM-定例MTG.md</code></td></tr>
    <tr><td class="name">定例MTG実施</td><td>人間</td><td>—</td><td>—</td></tr>
    <tr><td class="name">定例MTG議事録作成</td><td>AI</td><td>meeting-minutes-creator</td><td><code class="mono">Output/議事録/YYYY-MM-定例MTG.md</code></td></tr>
    <tr><td class="name">月次レポート作成</td><td>AI</td><td>—</td><td><code class="mono">Output/YYYY-MM-月次レポート.md</code></td></tr>
  </tbody>
</table>

<h3 class="sub-head"><span class="num">3.2</span>B. {{活動カテゴリ名}}</h3>
<!-- A と同形式。支援内容に応じて必要な数だけカテゴリを追加する -->

<h3 class="sub-head"><span class="num">3.N</span>Z. 改善イニシアチブ（随時）</h3>
<p>新たな施策・改善提案が必要になった際に起動する。</p>

<table class="report-table">
  <thead>
    <tr><th>活動</th><th>担当</th><th>連携スキル</th><th>成果物格納先</th></tr>
  </thead>
  <tbody>
    <tr><td class="name">イニシアチブ提案書作成</td><td>AI</td><td>project-proposal</td><td><code class="mono">Output/提案-{イニシアチブ名}.md</code></td></tr>
    <tr><td class="name">施策実施・進捗管理</td><td>人間+AI</td><td>—</td><td><code class="mono">Work/{イニシアチブ名}/</code></td></tr>
    <tr><td class="name">施策振り返りレポート</td><td>AI</td><td>—</td><td><code class="mono">Output/振り返り-{イニシアチブ名}.md</code></td></tr>
  </tbody>
</table>
```

## 状態管理の方法

活動カタログの各行はステータスを持たない（順序・進捗の概念がないため）。状態は以下の2層で管理する。

| 対象 | 管理方法 |
|------|---------|
| 単発で完結する活動 | 完了時に第6.2節の履歴ログへ1行追記するのみ |
| セッションをまたぐ活動 | 第2節「進行中の活動」表でステータス管理し、完了時に表から削除して履歴ログに記録 |

「進行中の活動」のステータスは共通語彙を使う。

| ステータス | 説明 |
|------------|------|
| `in_progress` | 進行中 |
| `review_pending` | AIタスク完了、ユーザーレビュー待ち |
| `waiting_human` | 人間タスク待ち（クライアント返答待ち・外部パートナー待ち等） |

`not_started` の活動は表に載せない（カタログに存在すること自体が「起動可能」を意味する）。`completed` は表に残さず履歴ログで表現する。

## 大きな活動をサブプロジェクトに切り出す判断

活動が数ヶ月にわたり、独自のマイルストーン・成果物・リスクを持つようになったら `projects/{活動名}/` にサブプロジェクトとして切り出す。切り出したサブプロジェクトは自身の `workflow.html`（多くはチェックリスト型）と `プロジェクトサマリ.md` を持ち、親の「進行中の活動」表には1行だけ残してサブプロジェクトのパスを備考に書く。切り出しは第6.1節の重要な意思決定に記録する。

## PM 呼び出し時の扱い

活動カタログ型プロジェクトでは、自動ルーティングの「現在のステップ」に相当するものがない。PM は以下を行う。

1. 第2節「進行中の活動」表と第6.2節の履歴ログの直近数行を提示する
2. `review_pending` / `waiting_human` の活動があれば、通常どおりレビューゲート・完了報告の選択肢を提示する
3. なければ AskUserQuestion で「次に起動する活動」を活動カタログから選ばせる（月次サイクル活動の時期であればそれを最優先で提案する）

## 更新ルール

1. **活動の起動時**: セッションをまたぐ見込みなら第2節「進行中の活動」表に追加（`in_progress`）
2. **AIタスク完了時**: ステータスを `review_pending` に更新し、レビューゲートへ
3. **レビュー承認時**: 表から削除し、第6.2節の履歴ログに成果物パスとともに追記
4. **知識状態の変化時**: SKILL.md の自動同期ルールに従い `プロジェクトサマリ.md` を更新
5. **カタログの改廃**: 支援内容の追加・終了があれば第3節の行を追加・削除し、第6.1節の重要な意思決定に記録する
